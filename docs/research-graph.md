# Research note: graph navigation for interlinked technical documentation

Status: **v1 implemented** (deterministic links, link/impact API, Connections panel) and **v2: link-aware
search** (on by default; measured on a labelled synthetic wiki — docs/evaluation.md §6: multi-hop evidence
recall 0.24 → 0.60, single-hop unchanged, no leakage). Not yet done: shared-identifier / entity edges,
Graphify import, agent/MCP tools, real-corpus multi-hop evaluation.

## Implemented (v2): link expansion in search

`search._linked`: when the question names a document (title or file name; else the top result), the
passages of documents linked to/from it (one hop, both directions, readable only) are scored against the
question minus the seed names, one per linked document first, and fill up to 5 of 10 result slots
(badge "linked from …", `signals.linked_from`). Setting `graph_expansion` (Settings → Linked documents).
Arms tried and rejected are listed in the evaluation.

## How the graph is stored

No graph database: nodes are `documents` (and their `chunks`, for anchors), edges are rows in `doc_links`
(source chunk, kind, raw target, anchor). Targets are resolved at query time, so edges appear as soon as
the target is ingested and disappear with it; traversal is SQL (one query per hop, permission filter
inside). This keeps one store, one backup and one permission model; a dedicated graph engine would only
pay off for deep traversals over millions of edges, which documentation graphs do not need.

## Implemented (v1)

- Extraction at indexing time (`parsing.extract_links`, `RELATION_KEYS`): Markdown links
  `[x](path/file.md#anchor)`, `[[Page Title#anchor|label]]`, front matter `depends_on`, `related`, `calls`,
  `owned_by`, `part_of`, `see_also` (list or comma string). External URLs and images are ignored.
- Storage: `doc_links` (migration 0004), one row per link per chunk, rebuilt/deleted with the chunks.
- Resolution at query time: target = file name (with/without extension) or document title,
  case-insensitive; `#anchor` → the chunk with that heading anchor; unresolved targets are reported.
- API (`graph.py`): `GET /api/documents/{id}/links` (outgoing, incoming, unresolved) and
  `GET /api/documents/{id}/impact?depth=1..3&kinds=…` (breadth-first blast radius over incoming edges,
  ≤200 nodes). Every query/hop is limited to the caller's readable collections.
- UI: passage drawer → **Connections** (links from, linked from, depends on this) with click-through.
- Tests: `tests/test_graph.py` (extraction, anchors, unresolved, incoming, 2-hop impact, kind filter,
  restricted documents invisible, delete removes edges). Demo data: `fixtures/corpus/platform-wiki/`.

## Next: entity edges ("Graphify for documentation")

Graphify-style tools connect code through symbols (imports, calls). The documentation equivalent is
**shared identifiers**: `orders-svc`, `orders_db`, `POST /v1/orders`, `ERR-PAY-4012`, table and config names
are already extracted per chunk (`chunks.idents`). Plan: treat each rare identifier as an entity node
(edge `mentions` from every chunk containing it, weighted by rarity), surface "also mentioned in" in
Connections and use it as a second expansion source; import Graphify's own graph export when a user has
one (format to be verified before building an importer). Accept only if it beats links-only on the same
evaluation without single-hop or permission regressions.

## Problem

Technical knowledge (codebase wikis such as those generated by Graphify / the codebase-documenter skill,
architecture docs, runbooks, API references, business workflows) is a *web*: pages link to each other,
share identifiers (service names, tables, endpoints, error codes) and form clusters (a module, a
workflow, a bounded context). Many valuable questions follow those links:

- "What breaks if the `orders` table schema changes?" (blast radius)
- "Which services call the payments API, and who owns them?" (from → to, ownership)
- "Walk me through the checkout workflow end to end." (path across several pages)

Flat chunk retrieval finds the *page* that mentions a term; it does not follow `depends on`, `calls`,
`owned by` or "see also" links. That is where graph structure helps.

## Principle: deterministic links first, LLM extraction last

Classic GraphRAG asks an LLM to extract entities/relations from every chunk — slow on CPU, error-prone,
hard to keep permission-safe and fresh. Technical docs already *contain* the graph explicitly, so build
it deterministically at ingestion time (cheap, exact, re-buildable):

| Edge source | Example | Edge kind |
|---|---|---|
| Markdown / wiki links | `[Orders API](../api/orders.md#void)`, `[[Payments Service]]` | `links_to` (to document + anchor) |
| Front matter relations | `depends_on: [payments-svc]`, `owner: team-billing`, `related: [...]` | typed, as declared |
| Shared rare identifiers | two pages both mention `orders-svc` / `ERR-PAY-4012` / `invoices.void` (already extracted per chunk as `idents`) | `mentions_same` (weighted by identifier rarity) |
| Generated structure (Graphify output) | node/edge exports for modules, call/dependency graphs | typed, imported as-is |
| Heading hierarchy | section → subsection | `parent_of` (already implicit in `heading_path`) |

LLM-extracted relations (GraphRAG, LightRAG, HippoRAG) become a later *comparison arm*, not the foundation.

## Proposed design (fits the current architecture, no new database)

- Table `doc_links(src_document, src_chunk, dst_document, dst_anchor, kind, label, weight)`, filled by the
  parser (links/front matter) and an identifier co-occurrence pass; rebuilt with the document version
  (same atomic swap as chunks), deleted with the document.
- **Permission rule:** an edge is usable only if *both* ends are readable by the caller; every hop of
  every traversal filters on the caller's collections (recursive CTE with the collection filter inside).
- Retrieval uses:
  1. **Link expansion:** after hybrid retrieval, add 1-hop neighbours of the top passages as candidates
     (badge "linked from …"), then rerank/gate as usual.
  2. **Related panel:** passage view lists incoming/outgoing links so people (and agents) navigate the
     cluster like a wiki.
  3. **Blast radius / path queries:** bounded-depth (≤3) traversal over typed edges (`depends_on`,
     `calls`, `owned_by`) from an identifier or document, returning the evidence chunks for each edge.
  4. **Agent navigation (second brain):** expose `search`, `get_passage`, `get_links` as tools (REST/MCP)
     so a local or approved LLM can follow links the way Claude navigates a Graphify wiki — likely the
     biggest quality gain per unit of effort, and it reuses the same permission-filtered endpoints.

## Evaluation plan (decides adoption)

1. Corpus: run the codebase-documenter / Graphify skill on 1–2 public repositories → Markdown wiki
   (hundreds of interlinked pages). Plus a set of runbooks/workflow docs.
2. Questions: ~60 labelled, in classes — single-hop lookup, multi-hop (2–3 links), blast radius,
   ownership/from→to, workflow walk-through, unanswerable/hard-negative. Labels = the *set* of passages
   needed.
3. Arms: hybrid (today) · hybrid + 1-hop link expansion · + typed traversal · agentic navigation with a
   local LLM · (optional) LightRAG-style LLM-extracted graph.
4. Metrics: evidence-set recall@k (all required passages retrieved), precision, abstention false-answer
   rate, latency, indexing cost, behaviour under permission restrictions (no leakage through edges).
5. Adopt an arm only if it beats hybrid on the multi-hop classes without hurting single-hop or safety.

## Open questions

- Graphify output format to import directly (node/edge JSON?) vs re-deriving from the Markdown links.
- Edge freshness when only one end changes; dangling links (target not ingested / not readable).
- UI: graph view vs. "related" list — start with the list (cheaper, accessible), add a graph view only if
  users need it.
